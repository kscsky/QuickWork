# PRD · 知识蒸馏管道(Knowledge Distill)

> 状态:草案 v1(2026-09-08)· 讨论存档,待排期
> 一句话:**生成权给 agent,发布权给人,检索只信人审过的。**

## 问题

agent 开发任务里产出大量业务认知(为什么这么改、和谁耦合、踩过什么坑),现状两条路都堵:
自动沉淀 → 错误逻辑污染知识库(不可接受);
纯靠人写 → 没人写(组织记忆持续流失,"找到五年前写这代码的人请他吃饭")。

## 角色与闭环

| 角色 | 动作 |
|---|---|
| 开发 agent | 任务收尾/对话结束 → 生成沉淀**草稿**(draft,不入检索) |
| 卡负责人/工作区成员 | 点「阅读并沉淀」→ **编辑态抽屉**把关 → 发布(published) |
| 问系统消费者(人/agent) | 检索仅命中 published 条目;"ask"入口走 pgvector+全文 |

闭环:`生成 → draft → 编辑态把关 → 发布 → (新对话)重新生成 → delta 对比 → 换版发布`

## 五条铁律(交互设计原则)

1. **沉淀按钮必须是编辑态,不是 approve 键** —— 抽屉左草稿右可编辑,确认挂在"改完提交"上;纯 approve 按钮会在第 20 次之后被无脑点穿(自动化偏差)
2. **草稿带出生证明** —— front-matter 记 source run / issue / jira_key / 模型 / 时间;错误知识必须可回溯到生成现场
3. **重新生成给 diff 不给全文** —— 人审 delta 的意愿是审全文的十倍
4. **冲突强制并排裁决** —— 同 module+topic 且相似度高 → "对比发布"视图,禁止静默覆盖;两道结论矛盾是常态不是异常
5. **draft 不进检索,但要防腐烂** —— 站报/企微周报带"待沉淀 N 条,最老 X 天";闸门没有水位计就会变淤坝

## 生成入口(双轨)

- **人工触发**:issue 详情 / 评审报告 / chat 末尾 →「沉淀此卡结论」→ 平台派发一次生成 run
- **约定触发**:开发 agent 的 instructions 红线里加一条"交付时若产生可泛化认知,顺手落 draft"(复用 dev-workflow 的 skill 契约机制,只产草稿,永远无权发布)

## 数据与归属

- **状态机在 QuickWork Postgres**(draft/published/retired + revision 链):按钮、diff、冲突、检索索引全在服务端
- **published 单向导出 git**(`<docs-repo>/docs/kb/<module>/`):人读、评审顺带、长期可读;git 永远不是编辑入口,避免双真源

## 非目标(v1 明确不做)

自动发布;冲突自动合并;跨 workspace 共享知识;wiki 类富文本编辑器。

## 验收场景

1. 开发对话结束,agent 落 draft;人在卡上打开抽屉,改两处后发布;5 分钟后 chat「问系统」命中该条并引用出处
2. 一周后新对话点「重新生成」→ 界面只给 3 处 delta → 人采纳换版,旧版入 revision 链
3. 新 draft 与已发布结论矛盾 → 冲突标记 → 并排对比视图强制人工裁决,无任何一条被静默改写

## 里程碑

| | 内容 | 判据 |
|---|---|---|
| M1 | draft 生成 + 编辑抽屉 + 发布 + published 检索 | 场景 1 全链路走通 |
| M2 | 重新生成 delta + 冲突对比裁决 + revision 链 | 场景 2、3 |
| M3 | git 导出 + 防腐周报 + agent 侧自动 draft 契约铺开 | 知识库仓周更、草稿积压清零 |
