# 技术方案 v2 · 看板泳道列(「可沉淀」与内置列同机制)

> 2026-09-08 · 用户已拍板:要一等列(独立分页/计数/拖入拖出与内置列同机制),本期只做一条泳道,机制自然承接第二条。
> 行为层零改动:distill 仍是 done 类目;触发钩子、点火规则、统计口径、GC 全部现状保持。

## 改动的三个面(全部,不多做)

### A. 服务端:列查询给"状态键"开一个维度(纯加法)
- 列分页接口(前端按列拉卡的那个)现在按类目过滤:`status IN (类目keys)`
- 新增两个可选请求参数:`only_status_keys`(只要这些键)/ `exclude_status_keys`
- 泳道列请求:`category=done, only=["distill"]`;已完成列请求:`category=done, exclude=["distill"]`
- 不传参数=行为与今天逐字节一致;老前端零感知
- 验收:S1 curl 对拍(排除前后 done 列计数 = 排除后 done + distill 之和)

### B. 前端:每列游标从"以类目标"改"以列标"
- 现状:每列的加载游标/页态记在 `Record<类目, ...>` 里——7 个键是写死的类型
- 改为:记在 `Record<列id, ...>`,内置列 id 恒等于 `status:<类目>`(行为不变,只是键名平移),泳道列 id = `status:<状态key>`
- 列清单来源:状态目录接口里读"启用的泳道键"(v1 用部署常量 `KB_LANE_KEYS=["distill"]`,工作区没建 distill 状态时自动为空=完全原样)
- WS 增量:status_changed 事件按"卡当前状态落在哪个列的谓词"重新归列(谓词=类目匹配±泳道认领,单函数收口)
- 验收:S2 完成后 UI 肉眼与改前无差(泳道常量置空),这是硬性回归门

### C. 拖放:落点带自己的"目标状态"
- 拖入列时写的状态值从"列的类目"改为"列声明的目标状态"(内置列:类目同名 key;泳道列:distill)
- 拖出泳道进任意常规列=现状行为(写该列 key),`status_changed→distill` 出列同样被钩子忽略(钩子只对"进入 distill"反应,已实现)
- 乐观更新回滚:旧列归属恢复按列 id 走(与 B 同源)
- 验收:S3 拖入→存根评论→沉淀中徽章→草稿落库→拖出,全链人肉走一遍
